# Google カレンダーは使うときに読み、変更の通知も裏での問い合わせも使わない

カレンダーを Google Calendar API で読むときは、予定が使われるとき(カレンダーの画面を開く、カードを出す、モデルがツールで予定を見る)にだけ問い合わせる。Google からの変更の通知(push)は使わず、裏で数分ごとに問い合わせることもしない。通知を受けるには、Google から届く公開の受け口と、そこから利用者のコンピュータへ知らせるつなぎっぱなしの接続が要り、利用者ごとの状態を持つ ASIST のサーバーを置くことになるからである。裏での問い合わせは、API の回数の上限を、画面を見ていない利用者の分まで使う。上限は Google Cloud のプロジェクト全体で1日100万回で、この1日の上限は申請しても増やせない(1分あたりはプロジェクトで1万回、利用者ごとに600回)。1日に100万回を利用者の数で割った回数が、1人が使える回数になる。

1回の使用で送るのは、状態の確認が予定表の一覧の1回、予定の読み出しが選んだ予定表ごとに1回(1ページ2500件まで)である。予定の変更は、状態の確認1回、変更前の予定とその予定表の読み出し2回、書き込み1回の計4回になる。アクセストークンの更新はプロセスごとに1時間に1回ほどで、トークンのエンドポイントはこの上限に数えられない。予定表の色は取りに行かない(`colors.get` も呼ばない)。画面の色はテーマの色で決めるからである。

## 見送った案

- **syncToken で前回からの差分を取る。** 差分を取るにも、使うたびに予定表ごとに1回問い合わせるので、回数は期間を指定して読むのと変わらない。そのうえ最初の同期で予定表の全期間(繰り返しの予定を1件ずつに展開したもの)を読み、その写しを手元に持ち続けることになる。ASIST の読み方は、画面の月や週、カードの今日や今週という期間ごとなので、期間を指定して読む。
- **変更の通知(push)を受ける。** 上に書いたとおり、公開の受け口と利用者ごとの状態を持つサーバーが要る。
- **裏で定期的に問い合わせる。** 使っていない時間にも上限を使い、利用者が増えるとプロジェクト全体の1日の上限に届く。

## 分かっている制約

- ほかの端末や Google カレンダーの画面での変更は、次に予定を使うときまで ASIST に届かない。開いたままのカレンダーの画面は、開き直すか、表示する期間を変えたときに読み直す。
