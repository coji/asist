# Windows では、Agent の CLI を、Job Object を持つ起動用のプログラムから動かす

Windows では、Agent の CLI を ASIST が直接起動せず、同梱した `asist-agent-launcher.exe` から起動する。launcher は、トークンを名前に入れた Job Object を作り、標準入力で `start` を受け取ってから、CLI を最初から Job の中に作る。CLI が起動したプロセスも、親子のつながりが切れても同じ Job に入る。launcher は、CLI が自分で終わったとき、`--stop` で止められたとき、ASIST のプロセスが終わったときのどれでも、Job が空になってから終わる。そのため ASIST は、launcher が終わったことを、CLI とその子孫がすべていなくなったこととして扱える。再起動のあとは、保存したトークンから Job の名前を決めて、その Job だけを止める。Windows にはプロセスグループとグループへの信号が無く、親子のつながりをたどるだけでは親が先に終わった孫を取りこぼし、PID はすぐ再利用されるので PID と時刻では自分のプロセスだと確かめられない。macOS の、プロセスグループと環境変数のトークンで確かめるやり方は、そのまま使う。

## 見送った案

- **`taskkill /T /F` で止める。** 生きている親子のつながりしかたどれず、自分で終わった CLI が残した孫を取りこぼす。
- **main から FFI で Job Object を扱う。** `spawn` のあと Job に入れるまでのあいだに、CLI が子を作れてしまう。これを防ぐには起動用のプログラムがどのみち要る。
- **PowerShell の `Get-CimInstance Win32_Process` で調べる。** 起動に時間がかかり、親子のつながりが切れた子孫が自分のものかを確かめられない。
- **ASIST と launcher を名前付きパイプでつなぎ、止める指示と ASIST の終了をパイプで伝える。** ASIST の終了は ASIST のプロセスのハンドルを待てば分かり、止める指示は名前から Job を開く `--stop` で足りる。

## 分かっている制約

- SIGTERM にあたるものが無いので、CLI に片づけの時間を与えずに止める。CLI が worktree に残した一時ファイルやロックのファイルは、取り込みや破棄のときの git の確認で見つかる。
- Job に入るのは、CLI とその子孫が自分で作ったプロセスだけである。タスク スケジューラ、WMI、COM のサーバーのように、Windows のサービスやすでに動いているほかのプロセスに頼んで作らせたプロセスは、Job の外にでき、止めるときにも残る。
- npm で入れた CLI は `.cmd` しか無く、使えない。`.cmd` は `cmd.exe` を通してしか起動できず、ASIST が渡す引数の引用符や括弧を `cmd.exe` が読み替えるためである。
