# me.md と user.md を毎回の会話に載せてそれぞれをトークンの上限に収め、忘れるための仕組みは持たない

毎回の会話のシステムプロンプトには、`me.md` と `user.md` を丸ごと載せる。会話のエンジンでも Gemini Live でも同じである。ASIST の人柄とこの人との関係(me.md)と、この人についての事実(user.md。たとえばアレルギー)は、発話の言葉がたまたまその見出しに当たったときだけでなく、どの会話でも効いていなければならないからである。本人に頼まれたことと避けてほしいと言われたことは、user.md の「ASIST への期待」に書き、本人が会話で取り消すまで残す。ページと日記はこれまでどおり、発話に関係するものだけを検索して会話に添える。me.md と user.md は検索の索引に入れないので、発話への注記にも recall の結果にも出てこない。毎回の会話に丸ごとある文を検索でもう一度添えても、同じことを二度読ませるだけだからである。

Gemini Live のセッションは、再開すると最初に開いたときのシステムプロンプトのまま続く。そこで ASIST は、再開のためのハンドルごとに、そのセッションが読んだ me.md と user.md を覚えておく。記憶の画面での保存や取り込んだ整理で二つが変わっていたら、次にセッションを開くときは再開せず、今の二つを載せたシステムプロンプトと最近の会話で新しく開く。二つが変わるのは一日に数回までなので、再開しないで開く手間は小さい。

二つのファイルには、それぞれ 3000 トークンの上限がある。書き足されるにつれて毎回の会話が重くなるという心配には、この上限で答える。トークンは、文字の種類(かな、漢字、ハングル、デーヴァナーガリー、ラテン文字、数字と記号など)ごとの重みで見積もる。整理の Agent が動く場所で本物のトークナイザーを動かせる保証は無く、会話のモデルもプロバイダごとに数え方が違うので、どのモデルの数にも足りないことの少ない軽い見積もりを、整理のスクリプトと ASIST の両方で使う。上限は言語ごとに変えない。見積もりが文字の種類ごとの重みを持っているので、同じ上限で毎回の負担はどの言語でもほぼ同じになる。3000 トークンは日本語でおよそ 4000 字、英語でおよそ 1800 語にあたる。

上限は書く側で守る。整理のスキルには数えるスクリプトと書き方を確かめるスクリプトがあり、Agent は終える前にそれを実行して、上限に収まるまで縮める。二つのスクリプトは Python で書き、ASIST が同梱する uv で、ASIST が userData に入れる Python の上で動かす。codex や claude を公式のインストーラーで入れた人のコンピュータには、Node も Python も無いことがあるからである。ASIST は Agent の PATH の先頭に uv を置き、uv にはその Python だけを使わせてダウンロードもさせないので、Agent のコマンドはネットワークの無いサンドボックスの中でも動く。Python は Agent を起こす前に ASIST が入れる。ASIST 自身は同じ規則を TypeScript で持ち、数え方の値は二つが読む一つのファイルに置き、規則は二つが同じ答えを返すべき例の集まりで確かめる。ASIST も同じ数え方で、上限を超えるファイルを残す整理を取り込まず、記憶の画面で上限を超える保存を断り、何トークン多いか、およそ何字削ればよいかを示す。上限を超えたファイルを会話に載せるときは、切らずに丸ごと載せる。上限ができる前から長いファイルは、次の整理が縮めるまでそのまま載る。

以前の `instruction.md`(いつも覚えておくこと)は持たない。ASIST は記憶を開くときに、その「私について」の節を me.md に、ほかの節を user.md に、文をそのまま移して消し、一つのコミットにする。本人が書いた文も含めて何も失わず、移した節は次の整理がそれぞれの見出しに収める。

記憶を忘れるためのツールとファイルは持たない。本当に消したい記憶は、ユーザーが記憶の画面で消す。会話の中で「今の忘れて」と言われた話は、整理の Agent が日記やページに書かない。会話に出てきたことが記憶に残るかどうかはもともと確率的なので、これで足りる。

## 見送った案

- **毎回の会話に載せるのは instruction.md だけにし、user.md と me.md は検索で引く。** 2026-10-02 までの決定で、ファイルが書き足されるにつれて毎回の会話が重くなるのを避けるためだった。しかし、アレルギーのような事実や ASIST の人柄が、発話の言葉が見出しに当たらない会話では効かなかった。重さは上限で抑えられる。
- **instruction.md も me.md と user.md と一緒に載せる。** instruction.md の「この人について」と「私について」は user.md と me.md の要約なので、同じ事実が毎回二度載る。実際の記憶では、三つの節の文字の並び(連続する二文字)の 84〜91% がすでに user.md か me.md にあり、無関係な文章でも 24〜42% は重なることと比べても、ほとんどが重複だった。残る「頼まれていること」には、user.md の「ASIST への期待」という置き場がもともとある。
- **instruction.md の中身の移し替えを、次の整理の Agent に任せる。** Agent が文を落としても、気づく手段が無い。ASIST が文をそのまま移せば失うものは無く、整え直しだけを Agent に任せられる。
- **整理のスクリプトを node で動かす。** 以前の validate.mjs はそうしていた。Node の無いコンピュータでは Agent が自分の書いたものを確かめられず、上限を超えた整理はすべて取り込まれずに終わる。
- **本物のトークナイザーをスキルに同梱して数える。** o200k の語彙だけで数 MB あり、Claude や Gemini とも数え方が違うので、文字の種類ごとの見積もりより正しいとは言えない。
- **UTF-8 のバイト数を 4 で割って見積もる。** ASIST がほかの場所で使っている見積もりだが、ヒンディー語を o200k の 1.5〜2 倍に数えるので、その言語でだけ書ける量が半分近くになる。
- **上限を超えたファイルは、上限で切って会話に載せる。** 黙って記憶の一部を落とすことになる。
- **会話から記憶を消すツール(`forget_memory`)と、消したことを書き残すファイル(`forget.jsonl`)。** 消すのは記憶の画面で足りる。
- **記憶の画面で消したときだけ `forget.jsonl` に書き、次の整理で作り直されないようにする。** 仕組みを単純にすることを選んだ。

## 実測

2026-10-02 に測った。見積もりと実際のトークン数の比は、アプリの辞書と説明書きと記憶の例文から作った 82 の文章(会話の11言語)で、o200k(OpenAI と gpt-oss)に対して日本語 0.94〜1.13、韓国語 0.97〜1.13、ヒンディー語 0.95〜1.19、英語 1.07〜1.27、ほかのラテン文字の言語 0.94〜1.21 だった。Gemini 3.8 Flash の countTokens に対しては、どの言語でも 0.94 以上だった(日本語では Gemini の数は o200k の約 0.8 倍)。Qwen3 のトークナイザーはヒンディー語をこの見積もりの約 2.4 倍に数える。Claude のトークナイザーは測れなかった。実際に使われている日本語の記憶の三つのファイル(1140〜2463 字)では、見積もりは o200k の 1.01〜1.02 倍だった。

Gemini Live(gemini-3.8-live)のセッションを開いてから setupComplete が届くまでの時間は、各10回の中央値で、記憶なし 630 ms、instruction.md の大きさ(Gemini で 688 トークン)の記憶 634 ms、instruction.md、me.md、user.md の三つ(3056 トークン)643 ms、三つを 1500 トークンずつ近く(3302 トークン)まで 666 ms だった。ばらつき(540〜770 ms)の内に収まった。同じ日のあとで測り直すと、記憶なし 692 ms、三つ(3056 トークン)662 ms、二つを 3000 トークンずつ近く(Gemini で 4531 トークン)まで 713 ms で、これもばらつき(626〜1066 ms)の内だった。記憶を載せても開くのは遅くならない。

整理の Agent のコマンド(`uv run --no-project <スクリプト>`)は、PATH にあるのが同梱の uv とシステムのフォルダだけで、Python の置き場に書けないサンドボックスの中でも動いた。Python を入れるのは初回だけで、67 秒かかって 66 MB を置いた。入っていれば `uv python install` はネットワーク無しで 0.06 秒で終わる。`uv run` は初回 0.58 秒、二回目から 0.06 秒だった(uv 0.12.18、Python 3.12.14、Apple シリコンの Mac)。

## 分かっている制約

- 初めての整理の前に Python を取得するので、そのときネットワークが無いと整理は失敗し、翌日の 0 時にやり直す。
- 規則は TypeScript と Python の二つにあり、片方だけを直すと、共通の例の集まりのテストが落ちるまで食い違う。
- instruction.md の中身を移したあとの me.md と user.md は上限を超えることがあり、次の整理が縮めるまで、記憶の画面ではその文書を上限まで縮めないと保存できない。
- 記憶の画面でページを消しても、その話がまだ整理していない日の会話に出てくると、次の整理でページが作り直されることがある。
