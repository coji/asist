# ファイルのビューアの重い処理は、Web Worker ではなく、別のプロセスで動く iframe の中で行う

ファイルのカードと拡大表示のビューアが行う重い処理(文書を解析する、画像を復号する、ページを描く)は、アプリの画面の中に隠して置いた iframe の中で行う。この iframe には、main が `asist-preview://` という専用のスキームで配るページを読み込む。アプリの画面とはサイトが違うので、Chromium はこの iframe を別のプロセスで動かす。大きすぎるファイルでメモリを使い切っても、終わるのはこの iframe のプロセスだけで、アプリの画面と会話は続く。iframe が落ちたことは、返事を待っていた要求が失敗することでビューアに伝わり、ビューアはそれをエラーとして表示する。次の要求では新しい iframe を起動する。Web Worker を使っても画面のスレッドは止まらないが、Worker は画面と同じ renderer のプロセスで動くので、Worker がメモリを使い切ると renderer ごと落ち、画面が読み込み直されて会話が途切れる。

## 見送った案

- **Web Worker で処理する。** 解析のあいだも画面は止まらないが、Worker がメモリを使い切ると、画面の renderer のプロセスごと落ちる。

## 実測

2026-10-02、Electron 43.7.7、Apple M5(メモリ 32 GB)。iframe の中で配列を確保し続けて、V8 のヒープの上限(約 4 GB)まで使い切らせた。

- 開発版(`electron-vite dev`): iframe は画面とは別の renderer のプロセスで動き、何も開いていないときのメモリ(RSS)は 79〜84 MB だった。使い切ってから 2.0〜2.4 秒で、待っていた要求が失敗として画面に届いた。そのあいだ、画面で 10 ms ごとに動かしたタイマーの遅れは最大 3 ms で、画面は読み込み直されなかった。次の要求は新しいプロセスの iframe を起動し、54〜97 ms で返事が届いた。同じ画面で Web Worker に同じように使い切らせると、画面の renderer のプロセスが落ち(`render-process-gone`、reason は crashed)、画面が読み込み直された。
- 配布版(`npm run dist:mac:unsigned`、2 回): iframe は別の renderer のプロセスで動き、何も開いていないときのメモリは 78〜80 MB だった。iframe を起動してページから返事が届くまでは 46〜89 ms だった。使い切ってから 0.6〜0.7 秒で、iframe が落ちたことが画面に届き、タイマーの遅れは最大 1 ms で、画面は読み込み直されなかった。その直後に起動した新しい iframe は 58 ms で返事をした。ほかの処理で混んでいたとき(load average 約 30)は 1,064 ms かかった。

## 分かっている制約

- iframe は、どのビューアも文書を開いていないときには外す。開いているあいだは、そのプロセスの分、約 80 MB を余分に使い、外したあとに開くときは、iframe の起動に 50〜100 ms ほどかかる。
- このページは、許可したフォルダのファイルを、アプリの画面と同じく `asist-file://` で読める。そのため、main はこのページを埋め込めるのをアプリの画面だけに限り(`frame-ancestors`)、ページは自分を埋め込んだ画面からしか要求を受けない。ページとページが起動する Worker は、自分のスクリプトを動かすことと `asist-file://` を読むことしかできず、外のホストには何も送れず、新しいウィンドウも開けない。
- iframe が落ちたことは、Electron だけが持つ MessagePort の close イベントで知る。Chrome(154)にはこのイベントがないので、Chrome で開く demo では、iframe が落ちても待っている要求はそのまま返事を待ち続ける。
