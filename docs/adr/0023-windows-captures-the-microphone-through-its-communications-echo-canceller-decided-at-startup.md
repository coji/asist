# Windows では、マイクを Windows の通話用のエコーキャンセルを通して取り込み、使えるかは起動時に一度だけ決める

Windows では、同梱した `asist-mic.exe` が、既定のマイクを WASAPI の通話用(Communications)の分類で開いて取り込む。こうすると、Windows は通話用の処理(マイクのドライバーのもの、無ければ Windows 11 24H2 以降の Voice Clarity)をかけ、そのエコーキャンセルは既定のスピーカーに流れる音を参照にする。そのため、Chromium が鳴らす読み上げだけでなく、Windows の音声合成で読むシステムの声や、ほかのアプリの音も打ち消せる。getUserMedia の `echoCancellation: true` は Chromium 自身が鳴らした音しか打ち消さないので、Mac の voice processing と同じ働きをする経路を Windows にも用意した。ヘルパーとのやりとり(48kHz、モノラル、float32、終了コード)は Mac と同じにして、main と renderer は OS で分けない。この経路を使うかは、main が起動時に `asist-mic.exe --check` を1回動かし、そのストリームのオーディオ効果の一覧で Windows がエコーキャンセルを「有効」と答えたときだけ使う。その結果を capabilities の `nativeMic` にする。一覧に無いか無効なマシン、マイクが無いマシン、確認そのものが失敗したマシンでは、最初から getUserMedia で取り込む。

## 見送った案

- **Voice Capture DSP(`CLSID_CWMAudioAEC`)を使う。** 出力が 16kHz に限られ、48kHz のフレームを受け取る DeepFilterNet に渡せない。参照にする出力の側で何かが鳴っていないと動かないので、無音のストリームを流し続ける必要もある。
- **ヘルパーをいつも動かし、エコーキャンセルが効いていないと分かったら getUserMedia に切り替える。** マイクを入れるたびに失敗を待ってから切り替えることになり、失敗したときの代わりの動き(fallback)を足さないという方針にも反する。そのマシンで使えるかは起動時に一度確かめ、その OS とマシンの経路として決める。

## 分かっている制約

- 決めるのは起動時の一度だけである。起動したあとでエコーキャンセルのあるマイクに替えても、アプリを起動し直すまでヘルパーは使わない。
- 動いている最中にヘルパーが止まったとき、たとえば既定のマイクを替えた先でエコーキャンセルが無効だったときは、macOS と同じく renderer が getUserMedia に切り替える。
- 起動時の確認は、既定のマイクを開くだけで取り込みは始めないが、ウィンドウが出るのが最長で 5 秒遅れる。設定でエコーキャンセルを切っていても、確認は起動のたびに行う。
- Windows が「有効」と答えても、スピーカーで鳴らした読み上げをどれだけ打ち消すかは、まだ測っていない。Chromium の `echoCancellation: "all"`(Windows 11 ではシステム全体の出力を参照にする)と比べて、Windows の既定をどちらにするかを決める必要がある。
