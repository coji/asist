# ファイルのカードで開く HTML のページは、そのフォルダの中だけを読み込み、ネットワークから切り離したセッションで表示する

ファイルのカードで開いた HTML のページと、ブラウザがスクリプトを動かすその他のドキュメント(SVG など)は、`asist-file` で配るときに、そのファイルが入っているフォルダとその下だけを読み込める CSP(`documentPolicy`)を付けて配る。読み込めるのは自分のフォルダのスクリプト・スタイル・画像・フォント・メディアと、ドキュメント自身が持つ `data:` と `blob:` だけで、ほかのフォルダのファイルも、外のサーバーの資源も読み込めない。`connect-src 'none'` で `fetch`・`sendBeacon`・WebSocket をふさぎ、フォームの送信、フレーム、ワーカーからの外への通信もふさぐ。CSP の source はホストを必要とするが、ローカルのパスの `asist-file` URL にはホストが無いので、空のホストの代わりに `*` を置き、パスでフォルダに閉じ込める。Windows の共有のときはサーバー名をそのままホストにする。

そのうえでページは、アプリの画面と同じセッションの iframe ではなく、ネットワークから切り離した専用のセッションの `<webview>` で表示する。CSP が及ばない通信が二つあるためである。一つは `<link rel="dns-prefetch">` で、ページが選んだホスト名を OS の名前解決に問い合わせる。もう一つは WebRTC で、CSP とは関係なく、ページが指定したどのアドレスへも UDP と TCP で送信できた。main はアプリの画面のすべての `<webview>` をこのセッションに付け、ページの描画プロセスでは DNS の先読みを切る(`--blink-settings=dnsPrefetchingEnabled=false`)。セッションは `asist-file` 以外の要求をすべて取り消し、要求ではない接続(WebRTC の TCP)を接続先のないプロキシ(`127.0.0.1` のポート 0 で、OS がパケットを出す前に断る)へ向ける。このとき Chromium がこの Mac 宛てだけ直接つなぐ例外は外す。WebRTC の UDP は止める。ページが自分で始める移動、新しいウィンドウ、権限の要求もすべて断る。CSP の `sandbox allow-scripts` はページのオリジンを不定にし、ポップアップとフォームとダイアログを止める。webview はプリロードを持たない別の webContents なので、ページはアプリの画面にも preload のブリッジにも触れられない。アプリの画面の `frame-src` には `asist-file:` を入れず、ファイルのドキュメントがアプリのセッションで表示されることはない。

## 見送った案

- **これまでどおり、CDN からスクリプトやスタイルを読み込めるようにする(`script-src`/`img-src` などに `https:`、`connect-src https:`)。** レポートがグラフの部品を CDN から読むためという当初の許可だったが、外の https へ出す口はそのまま、読み取った中身を外へ送る口になる。「外へつなげない」ことと「任意の https を読み込める」ことは両立しないので、外部の読み込みはやめ、ドキュメントは自分のフォルダの中で完結させる。
- **サブリソースの要求ごとに、main 側でもページのフォルダの外を拒む。** `asist-file` の要求にはどのページが出したのかが載らない(Referer を付けず、オリジンも不定)ので、要求ごとにページのフォルダを知る術がなく、これを入れるにはこの scheme の作り直しが要る。閉じ込めで読めるものを外へ送る口はすべて閉じてあるため、下の制約の範囲で別の許可フォルダの中身がページに読めても、それを持ち出すことはできない。そこで main 側の追加の確認は入れず、読める範囲を下に明記するだけにした。
- **iframe のまま、アプリ全体で DNS の先読みを切る。** dns-prefetch は止まるが、WebRTC は止まらない。WebRTC の TCP をプロキシで止めるにはセッション全体のプロキシを変えるしかなく、アプリの画面の通信まで止まる。
- **アプリ全体の名前解決を、存在しない DNS over HTTPS のサーバーに向ける(`app.configureHostResolver`)。** アプリのほかの通信の名前解決もすべて止まり、dns-prefetch もその DNS over HTTPS のサーバーへの接続を試みる。
- **`WebContentsView` で別の webContents を窓の上に重ねる。** 窓の決まった位置に描かれる面なので、カードのスクロールや下端での切り取り、フォーカス表示との重なりに合わせられない。`<webview>` は iframe と同じように画面の中に並ぶ。

`href="//prefetch-check.invalid"` の dns-prefetch は、相対の URL として `asist-file` に解決されるので、どの形でも問い合わせなかった。この Mac 自身(`127.0.0.1`)への WebRTC の TCP は、Chromium の例外を外すまで、プロキシがあってもつながった。採用した形では、ページ自身への移動、meta refresh、`window.open`、speculation rules、`ping`、WebSocket、`fetch` と `sendBeacon`、favicon と manifest、`rel="prefetch"`、about:blank の iframe からの `fetch` も、問い合わせも接続もしなかった。これらは CSP と移動の拒否を外しても、採用した形のセッションだけで問い合わせも接続もしなかった。開発版のアプリと、`npm run dist:mac:unsigned` で作った配布版のアプリでも、採用した形の行と同じ結果になった。

表示までの時間(要素を加えてからページのスクリプトが動くまで、5 回)は、iframe で 52〜82 ms、webview で 71〜94 ms だった。アプリのカードでは、カードを開いてからページのスクリプトが動くまで 115〜129 ms だった。メモリは、どちらもページのためのプロセスが一つ増え、全体で約 134 MB(アプリでは約 125 MB)増える点で同じだった。専用のセッションそのものは約 1 MB だった。

## 分かっている制約

- ページは外部の資源を読み込めないので、CDN のライブラリに頼るレポートは、部品を自分のフォルダに同梱するか、ページの中に埋め込む必要がある。
- 閉じ込めは CSP のパスで行う。同じフォルダの中にあるファイルどうしは、これまでどおり互いの中身を読める。ページのフォルダの中にある、別の許可フォルダを指すシンボリックリンク(クローンしたリポジトリや展開した zip の中など)をたどった先や、ページを広いフォルダ(たとえば Downloads)の直下に置いたときのそのフォルダ全体は、URL がそのページのフォルダの下に収まる限り読める。どちらも読めるだけで、外へは送れない。
- ページが ICE サーバーや相手の候補として書いたホスト名を、WebRTC が OS の名前解決に問い合わせることは残る。Electron にはこれをセッションや描画プロセスごとに止める設定がない。そのホストへは何も送られないが、問い合わせにはページが選んだ名前が載る。
