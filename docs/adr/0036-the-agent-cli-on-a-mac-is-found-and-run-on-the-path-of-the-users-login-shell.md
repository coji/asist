# Mac では、Agent の CLI を利用者のログインシェルの PATH で探し、同じ PATH で起動する

Finder や Dock から開いたアプリは、launchd から `/usr/bin:/bin:/usr/sbin:/sbin` だけの PATH を受け取る。npm で入れた codex は `#!/usr/bin/env node` で始まるスクリプトなので、この PATH で起動すると node が見つからずに終了コード 127 で失敗する。nvm、bun、pnpm が `~/.zshrc` で PATH に足したフォルダにある CLI は、見つけることもできない。そこで ASIST は、利用者の `$SHELL` をターミナルを開いたときと同じ対話のログインシェルとして起動して PATH を読み、CLI をその PATH のフォルダで探し、ジョブの CLI もその PATH で起動する。探すのと起動するのを同じ一回の答えから決めるので、見つかったと表示した CLI が起動すると動かない、というずれが起きない。答えは、設定の画面を開いて CLI を探し直すまで保つ。シェルを起動すると利用者の設定が毎回すべて走るので、ほかの設定を変えたときには探し直さない。アプリの状態は答えを待たず、答えが来るまでは CLI を探しているところだと伝え、答えが来たら状態を送り直す。会話とマイクの開始は状態を待つからである。シェルが時間内に答えないときは、CLI が決まった場所にあっても起動できない状態として表示し、ジョブを始めない。短い PATH のまま起動すると、npm の CLI も、エージェントが動かすコマンドも、同じ形で失敗するからである。

## 見送った案

- **決まった場所と `zsh -lc 'whence -p'` で探し、起動は短い PATH のままにする。** 対話でない zsh は `~/.zshrc` を読まず、`$SHELL` が zsh でない利用者の設定も読まない。見つけた CLI を短い PATH で起動するので、npm で入れた CLI は動かない。
- **解釈系の要るスクリプトの CLI を、Windows の `.cmd` と同じく起動できないものとして断る。** npm は codex の主な入れ方の一つで、それを断ることになる。
- **シェルに main で同期に問い合わせる。** 利用者の設定によっては秒単位でかかり、そのあいだ main のすべての処理が止まる。

## 実測

- `~/.zshrc` で nvm と pyenv を読み込む zsh が `-i -l -c` で PATH を返すまで、Apple Silicon の Mac で 0.55〜0.7 秒だった(2026-10-02)。時間の上限は 10 秒にした。

## 分かっている制約

- CLI を探すたびに、利用者のシェルの設定がすべて走る。その設定がエラーで止まるか 10 秒を超えると、Agent のジョブは始まらない。
- tcsh と csh は `-l` をほかのオプションと一緒に受け付けないので、対話シェルとしてだけ起動する。そのため `~/.login` で足した PATH は読まない。
- ジョブを作る処理はシェルの答えを待たない。そのため会話から頼むジョブは、確認画面を出す前に CLI を探し、起動できなければその場で断る。承認のすぐあとにジョブが失敗すると、承認がうまくいかなかったように見えるからである。誰も承認しない記憶の整理のジョブは、CLI が見つからなければ、始めたジョブがその理由で失敗する。
