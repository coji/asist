# その OS で使えない機能は、画面にもモデルのツールにも出さない

main が起動したときに一度だけ、その OS とマシンで使える機能を決め、renderer とモデルのツールはその値だけを見る。決めるのは、ローカルの音声認識と Qwen3-TTS を動かす GPU、エコーキャンセルのネイティブのマイク、グローバルショートカットのキーである。使えない機能は、選択肢もスイッチもカードもツールも出さない。ローカルの音声認識のように利用者が選ぶ場所のあるものは、その場所に使えない理由を出す。使えるはずの機能が失敗したときは、これまでどおりエラーとして見せる。ASIST が対象にしていない OS と CPU の組み合わせでは、使える機能を推測せずに起動を止める。出しておいて使うと失敗する形では、たとえば単体の GPU が無い Windows の初回セットアップで音声認識の準備が失敗し、利用者は失敗を見てからでないと先に進めない。

ASIST が対象にしているどの OS でも動く機能は、値にしない。どこでも同じ値になる判定は、通らない分岐を残すだけだからである。CPU で動く Python の worker(記憶の検索、相槌の分類器、MaAI)は Windows の CPU でも動くので、値にせず、どの OS でも出す。カレンダーも、どの OS でも Google Calendar API で読むので、値にしない。

## 見送った案

- **renderer に OS の名前を渡し、画面ごとに判定する。** 判定が画面の数だけ散らばり、モデルに渡すツールの一覧と画面の出し分けがずれる。

## 実測

2026-09-27、Windows 11、Core i9-9900K(8スレッド)で、`npm run dev` で起動したアプリから、CPU で動く3つの worker を準備して動かした。準備にかかった時間は、約 1.5MB/s の回線でのダウンロードを含めて、相槌の分類器が58秒、記憶の検索が59秒、MaAI が171秒だった。MaAI の worker は CPU で起動し、12秒の音声を実時間で流すと、80ms のフレームあたりの推論は中央値 59.8ms、90パーセンタイル 63.8ms、最大 66.7ms で、どれもフレームの長さに収まった。

## 分かっている制約

- 使えない機能が無い理由は、選ぶ場所のあるものにしか出ない。エコーキャンセルは、その OS では画面から消えるだけである。
