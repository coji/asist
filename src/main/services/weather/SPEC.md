# 天気カード

2026年9月15日。天気の取得はmainプロセスが行い、Agentへの結果とカードへ同じデータを渡します。カードの描画はrenderer、左右の配置・置換・拡大は共通カードが担当します。

## 取得元は地域の設定で決まる

2026年9月22日に追加しました。設定の地域が日本(`usesJmaWeather(region())`)なら気象庁を読み、それ以外の地域なら世界を対象にしたOpen-Meteoを読みます。判定は呼ばれるたびに行うので、設定を変えると次の質問から切り替わります。日本の動きは以前のままです。

どちらの取得元も `WeatherData`(`src/shared/weather.ts`)を埋めます。片方にしかない項目は `null` にし、カードは在るものだけを出します。気象庁の天気の言葉、発表時刻、観測所名、都道府県の風景、予報区と気温地点の行は日本だけにあり、Open-Meteoの風速と地名の国・州は日本以外だけにあります。無い項目を別の取得元の値や推測で埋めません。出典の行も取得元に合わせて変えます。

## Agentの入力と地域の解決

`show_weather({ location: "北海道", date: "today" })` のように呼びます。日付は `today` または `tomorrow` です。空欄、通称、現在地という文字列は、どの地域でも受け付けません。地域の既定値は持たないので、Agentは会話から場所を選び、根拠がなければ尋ねます。

日本では `location` に正式な都道府県名、市区町村名、または都道府県名を付けた市区町村名を指定します。日本以外では都市名を指定し、同名の都市があるなら国名を添えます。

- 都道府県は定義した代表市区町村へ解決します。通常はその地点の結果を伝え、確認を促しません。
- 一意な市区町村はその予報区へ解決します。
- 完全一致しなければ `location_not_found` と `hint` を返します。
- 同名の自治体が複数あれば `location_ambiguous` と都道府県付きの候補を返し、Agentがユーザーに確認します。
- 自治体一覧にはあるものの予報区域がない地域は `location_unavailable` を返します。予報区域のない自治体と同じ名前の自治体に予報区域があれば、その名前は予報区域のある方を指します。北方領土の国後郡泊村と後志地方の古宇郡泊村がこれにあたり、「泊村」も「北海道泊村」も古宇郡泊村になります。

日本語以外の会話では、モデルは「Sapporo」「Fuchu, Tokyo」のように地名をローマ字で書くので、ラテン文字を含む名前はローマ字の名前として引きます。

- 市区町村のローマ字の名前は、気象庁の英語名(`Sapporo City`)です。その英語名自体が、長音を「Minoh」「Kounosu」「Ota」と、b・m・p の前の音を「Tanba」「Gotemba」と書き分けているので、比べる前に一つの書き方にそろえます。そろえて同じになった場所は候補として返します。
- City や Town のような種類を表す語のない名前が都道府県の名前と同じなら、都道府県とします。英語で「Okinawa」と言えば、ふつうは県を指すからです。ただし、ほかの都道府県に同じ綴りの市区町村があれば、どちらとも決めずに候補を返します。2026年10月2日の表では、Ibaraki(大阪府茨木市)、Yamagata、Fukushima、Ishikawa の4つがこれにあたります。
- 種類を表す語のない名前を一つの市と町村だけが持つなら、その市とします。英語では市を種類を付けずに呼ぶからです。「Yokohama」は青森県横浜町ではなく横浜市です。同じ名前の市が二つ以上あれば候補を返します。
- 候補は日本語の都道府県名付きの名前で返します。英語名は都道府県を付けても一つに決まらないことがあるからです。北海道の江差町と枝幸町は、どちらも英語名が Esashi Town です。
- 神戸市と広島市の区は、気象庁が区ごとに予報するので英語名を持ち、「Higashinada Ward, Kobe」のように市の名前を付けると引けます。市の名前を付けないと引けないのは、「Naka Ward」だけでは、英語名を持たない横浜市中区などを指していても広島市中区を出してしまうからです。気象庁が市とまとめて予報しているほかの政令指定都市の区は英語名を持たず、日本語の名前でだけ引けます。

これらはツールの通常の戻り値です。警告ダイアログは出しません。地域が未解決の場合と全データの取得失敗時は、既存カードを変更しません。音声の途中から地域を推測する天気の投機表示も行いません。

日本以外では、場所を照合できる一覧を持たないので、取得の前に返す候補や曖昧さはありません。Open-Meteoのジオコーディングが一件も返さなければ、日本の一覧に無い名前と同じく `location_not_found` と `hint` を返し、どの都市・どの国かをユーザーに確かめるようAgentへ伝えます。表示中のカードを取り直したときに見つからなければ、カードには場所が見つからないことを表示します。

訂正するときだけ `replacesLocation` に前の地域を渡せます。その地域・対象日のカードが表示中なら、同じ位置で置き換えます。日本では同じ市区町村コードと対象日に同じカードキーを使い、都道府県指定とその代表市区町村指定も同じキーです。日本以外ではジオコーディングを二度行わずに置き換えられるよう、指定された場所の名前(前後の空白を詰め、小文字にしたもの)をカードの識別子にします。呼び方が違えば別のカードになります。

## 全国の対応表

`scripts/update-weather-regions.py` を開発時に実行して、国土地理院の自治体一覧と気象庁の区域・予報地点・観測所の対応表を結合します。生成した `src/main/services/weather/data/regions.json` をアプリへ同梱します。起動時や質問のたびに自治体一覧は取得しません。更新はスクリプトの再実行と検証後、アプリの更新で配布します。取得元とSHA-256は `data-sources.json` に保存します。

47都道府県と、政令指定都市の区を含む1,918件を収録しています。自治体コードは1件に1つで、国土地理院の一覧が旧コードでも載せている自治体(富谷市は富谷町だった頃の04423でも載っています)は1件にまとめます。都道府県は県庁所在地を代表とし、東京都は千代田区です。気象庁の市区町村区域から一次細分区域、担当官署へたどります。気象庁が区を市にまとめている場合は市の区域を使い、市が分割されている場合はコード順で先頭の区域を代表として選びます。分割地域を選んだことは戻り値に含めます。

市区町村の英語名は、気象庁の区域データ(`area.json`)が区域ごとに持つ `enName` から取ります。市区町村が複数の区域に分かれていると、区域の英語名は「Akan, Kushiro City」「Eastern Sendai City」「Kobe City Higashinada Ward」のように部分の名前を含むので、市区町村の名前の部分を取り出します。区域ごとに取り出した名前が一致しなければ、スクリプトは止まります。神戸市と広島市の区は「Kobe City Higashinada Ward」を「Higashinada Ward, Kobe City」の形に直して持ちます。2026年10月2日の生成では、1,918件のうち1,758件が英語名を持ちます。持たない160件は、市とまとめて予報される政令指定都市の区と北方領土の村です。

予報区域の代表アメダス観測所を現在の気温・湿度に使います。市役所から最寄りの観測所を検索する方式ではありません。たとえば東京都府中市の予報区は東京地方、観測所は東京です。カードには観測所名と予報の対象区域を表示し、Agentにも渡します。市区町村内で観測した値であるかのように説明しません。

## 取得するデータ

| 用途 | 気象庁のデータ | 扱い |
| --- | --- | --- |
| 日別の天気・最高最低・6時間降水確率 | `forecast/data/forecast/{code}.json` | 官署別に取得し、該当区域と地点を選びます。 |
| 週間の天気・気温・日単位降水確率 | 同じJSONの週間部分 | 通常と朝5時の区域集約に対応する候補から選びます。 |
| 3時間ごとの天気・気温 | `jmatile/data/wdist/VPFD/{area}.json` | 天気と気温の別々の時刻配列を時刻で結合します。 |
| 現在の気温・湿度 | `amedas/data/latest_time.txt` と観測所別3時間ブロック | 品質フラグ0の値だけを使い、30分を超える古い観測を採用しません。 |

担当官署のコードと配信用ファイルのコードが異なる十勝・奄美は、気象庁ページと同じ変換を行います。観測所は現在のアメダス一覧に存在するものを選びます。明日のカードは現在の観測値を表示せず、予報の最高気温を大きく表示します。

欠測や空文字は `null` です。0%、0℃、晴れに置き換えません。天気コードが未知なら天気情報を欠測として扱います。複合天気は複数のアイコンで表示し、「のち」は矢印で区別します。雨を強雨や雷雨へ勝手に変換しません。

発表時刻、観測時刻、アプリが取得を行った時刻を別々に保持します。取得元ごとの成功・欠測・失敗も保持し、一部だけ取得できた場合は残りを欠測として明示します。取得先の仕様変更により全て取得できない場合はツールを失敗にします。

## Open-Meteoから取得するデータ

鍵は要りません。ジオコーディング(`geocoding-api.open-meteo.com/v1/search`)を会話の言語で引き、最大10件の先頭を選びます。ただし設定の地域と `country_code` が一致する件の人口が先頭の10分の1以上あれば、そちらを選びます。同じ名前で同じくらいの規模の都市が複数あるときは、ユーザーのいる国の都市のことが多いからです。一方で、世界の都市と同じ名前の小さな町を選ばないために人口を比べます。2026年10月2日の返答では、地域の都市を選ぶべき例は先頭の7.1分の1以内(オンタリオ州のKingston、スペインのCórdoba、アラバマ州のBirmingham)、選ぶべきでない例は14.8分の1以下(スペインのGuadalajara、オンタリオ州のLondonは21分の1、テキサス州のParisは86分の1)でした。「Paris, France」のように国名をカンマのあとに添えた名前は、ジオコーディングがその国の中で引きます。選んだ都市の名前・州・国をカードのヘッダー右側に出し、どの場所を選んだかが分かるようにします。ジオコーディングの結果は24時間、予報は5分キャッシュします。

予報(`api.open-meteo.com/v1/forecast`)は1回の要求で現在・1時間ごと・日別を受け取ります。`timezone=auto` を付け、返ってきた時差(`utc_offset_seconds`)で現地時刻の文字列(`2026-09-15T18:00`)をISOの時刻に直します。Open-Meteo は、予報の期間の途中で時計が切り替わっても、すべての時刻をこの一つの時差で書きます。2026年10月2日に受け取ったシドニーの予報は、夏時間が始まる10月4日も +10:00 のまま書かれ、その夜の時計には無い 02:00 を含んでいました。過去の予報(`historical-forecast-api.open-meteo.com`)は、頼んだときにその場所で使われている時差で全体を書きます。2026年10月2日に頼んだヘルシンキの2026年3月27日からの7日間は、夏時間が始まる29日より前も +03:00 で、ミュンヘンの夏時間が終わった2025年10月26日をはさむ7日間は +02:00 で、どちらも1日を24時間として書かれていました。直したISOの時刻は正しいのですが、文字列の日付と時は、書かれた時差が使われていない時間帯では現地の時計と1時間ずれます。そのため、対象日も、各時刻がどの日のどの時にあたるかも、返ってきた時間帯の名前(`timezone`)で数えます。

| 用途 | Open-Meteoのデータ | 扱い |
| --- | --- | --- |
| 現在の気温・湿度・風 | `current` | 観測所の実測ではなく現在時刻の解析値なので、観測所名は持たせません。明日のカードでは表示しません。 |
| 時間ごとの天気・気温 | `hourly` | 対象日のうちまだ終わっていない時刻から、日本のカードと同じく現地の時計で3時間ずつに区切り、各区間の最初の時刻の値を出します。区切りは、今日のカードでは今の時刻から、明日のカードでは0時から数えて、時計の3時間ごとに置きます。時計が飛ばす時刻や繰り返す時刻は、それを含む区間の長さを変えるだけで、後の区間をずらしません。飛ばされた時刻から始まるはずの区間は、その次の時刻から始まります(ヘルシンキの2026年3月29日は0時、4時、6時、9時と続きます)。最後の区間はその日の終わりまでで、カードはその終わりを24時と書きます。次の日の0時を時計が飛ばす日(サンティアゴの2025年9月6日)は、その日の終わりが時計では1時になるからです。 |
| 降水確率 | `hourly.precipitation_probability` | 1時間ごとの値なので、各区間にはその区間で最も高い値を出します。区間そのものの確率ではありません。 |
| 日別の天気・最高最低・降水確率 | `daily` | 7日分をそのまま週間予報にします。 |

天気はWMO 4677のコードで返るので、`WMO_WEATHER` でアイコンと `cardsWeather.words.*` の語に対応させます。気象庁の日本語の天気名は使いません。一覧にないコードは欠測として扱い、近いコードに寄せません。霧と雹のアイコンは持っていないので、それぞれ曇りと雷のアイコンで描き、語で補います。コードは一つの状態を表すので「のち」は付きません。

単位は、地域が `US` のときだけ `temperature_unit=fahrenheit&wind_speed_unit=mph&precipitation_unit=inch` を付けて要求します。カードは返答の `current_units` と `hourly_units` が示す単位をそのまま持ち、摂氏のときは度記号だけ、それ以外は単位を添えて出します。降水量は表示しないので単位も使いません。

文章の概況、気象警報、発表時刻は公開されていないので、カードにもAgentの結果にも入れません。1回の要求で全部が返るため、取得元ごとの成否は `forecast` の1件だけになります。読めない返答や、対象日に天気も気温も時間予報も無い返答は、カードを出さずにツールの失敗にします。

## キャッシュとアクセス

mainプロセス内でURLごとにキャッシュします。気象庁の短期・週間・3時間予報とOpen-Meteoの予報は5分、アメダスの最新時刻と観測ブロックは1分、Open-Meteoのジオコーディングは24時間です。有効期間は定期巡回の周期ではありません。ユーザーの要求などで取得が必要になったときだけ使い、全国のデータを常時巡回しません。

同じURLへの同時取得を共有します。一人の待機者が中断しても他の待機者には影響せず、全員が中断した場合は通信を中断します。HTTPエラーと形式不正は保存しません。期限切れの成功値を取得失敗時に黙って再利用しません。アプリ終了時にキャッシュは消えます。

これらの期間はASISTの実装値で、気象庁やOpen-Meteoが許容頻度として保証した値ではありません。配布規模が大きくなった場合は、端末数に応じた総アクセス量と取得経路を再検討します。

## カードの表示

共通カードは左右に各1枚、最大2枚です。空いている位置を使い、両側が埋まっていれば古いカードをその位置で置き換えます。残るカードは移動しません。同じキーの更新は順番と位置を変えません。置き換えられたカードの拡大表示は閉じます。

天気カードは、対象日を「今日」「明日」と呼ぶかを、描くたびにその土地のいまの日付と比べて決めます。取得したときの今日・明日のままにすると、カードを出したまま日付が変わったときに前日を「今日」と呼んでしまうからです。日付が変わったあとは、前日のカードは日付だけを出し、明日のカードは「今日」になります。

天気カードは次の順に縦に並べます。

1. 風景と空模様をヘッダーまで連続させ、地域・対象日・気温・アイコンを重ねます。風景と空は共通カードの背景層に、日別予報の発表時刻はヘッダー右側の補足に置きます。右上の拡大・閉じる操作は共通カードを使います。
2. 最高最低、湿度、観測時刻・観測所を表示します。アイコン下の天気名や「サンプル」、カードごとの切り替え操作は置きません。
3. 時間予報を3時間単位で並べます。縦の区切り線を置かず、6時間降水確率は同じグリッドの下段で対応する2列をまたぎます。一部の時刻だけ表示するときも元の確率区間を保持します。
4. 週間予報を7列で表示します。幅が不足する場合は横にスクロールできます。
5. 出典と加工した旨、一部の取得に失敗した場合の状態を表示します。「—」を表示しているときだけ、出典の行に「— は未発表・欠測」を添えます。

日本以外のカードは、同じ並びのまま次の点が変わります。風景の画像は都道府県の分しか無いので、空だけを残して下端を地の色でぼかします。発表時刻は無いので、ヘッダー右側には選んだ都市・州・国を出します。観測所名も無いので、観測の行は「18:00 現在」のように時刻だけにし、その行に風速を続けます。予報区と気温地点の行は出しません。出典はOpen-Meteoへ差し替えます。

共通カードは、ドックの高さから大きさ(s / m / l)を決めてカードへ渡します。天気カードは大きさごとに次を出します。手順と数値は [skills/panel-card-design/SKILL.md](../../../../skills/panel-card-design/SKILL.md) にあります。

| 大きさ | 出すもの |
| --- | --- |
| l と拡大表示 | 上の1〜5を全部。予報区名と気温地点の行、週間予報の降水確率を含みます。 |
| m | 予報区名の行と週間予報の降水確率を畳み、上部の余白と気温の文字を少し小さくします。 |
| s | 週間予報を「週間の天気」の行に畳み、押すと拡大表示を開きます。時間予報と降水確率は残します。 |

都道府県の風景47枚と天気5種類を別々の画像として合成します。晴れは明るくします。昼用・冬用の風景は追加しません。透明PNGはアルファチャンネルと上部の透明領域を検査し、描かれたチェック柄の画像を採用しません。生成プロンプトは `src/renderer/src/assets/weather/landscapes/prompts.json` に保存します。

## 出典と検証

[気象庁の利用規約](https://www.jma.go.jp/jma/kishou/info/coment.html)に従い、「出典：気象庁」と「ASISTが加工・表示」を記載します。[利用上の留意事項](https://www.data.jma.go.jp/developer/ryuui.pdf)も参照し、値・対象区域を独自の予報へ改変しません。公開JSONは内容やURLが変更される可能性があります。

Open-MeteoのデータはCC BY 4.0です。配布元が求める「Weather data by Open-Meteo.com」をカードの出典に出し、リンクを付けます。日本語など他の言語では同じ意味の文にし、どの言語でも Open-Meteo.com の名前を残します。

地域解決、欠測、時刻の結合、観測品質、キャッシュ、カード置換、Agentへの未解決結果を単体テストします。Open-Meteo側は、記録した返答を使って取得元の切り替え、天気コードの対応、単位の要求、ジオコーディングの地域優先、エラーの種類を検査します。`WEATHER_LIVE=1 npx vitest run tests/weather-live.test.ts` は47都道府県の代表地点について実際の短期・週間・3時間予報を検査します。通常のテストでは外部へアクセスしません。市区町村全件の実取得を保証する検査ではありません。
